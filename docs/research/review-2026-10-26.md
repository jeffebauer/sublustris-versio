## 2. Where the CPU goes

**In one sentence:** the tank spends more time waiting for the external memory than doing sums, and the sums themselves run at about one instruction a cycle because the code hands the chip one long dependent chain at a time.

### 2.1 What the chip does with an instruction (the M7 facts used)

Everything below rests on these facts about the Cortex-M7, each with its source (full table in the `lit-m7` notes, Appendix A):

- **One floating-point add or multiply can start per cycle, and each takes 3 cycles to finish** ([quinapalus cycle counts](https://www.quinapalus.com/cm7cycles.html), measured on an H730; GCC's own M7 pipeline model `cortex-m7.md` says the same). So a chain of dependent FP operations runs at a third of the peak, and you need three or four independent chains in flight to fill the pipe.
- **Two FP operations never issue together; an FP operation and a load or store do** (quinapalus; an Arm Community thread on VFMA). Integer op + integer op pair; load + load don't.
- **A divide (VDIV.F32) costs 16 cycles of throughput, 18 of latency, and a square root 14/16**; the divider is not pipelined. Whether independent FP work can proceed behind a divide is **unverified** by any source found tonight; the profile build now has a MICRO test for it (section 3).
- **The data cache is 16 KB, 4-way, 32-byte lines, no automatic prefetcher** (ST AN4839 p. 4; Feabhas part 3). Only **two line fills can be outstanding** (Arm TRM Table 5-3). Every miss to SDRAM is an 8-beat burst on the 32-bit bus: about **53 cycles when the SDRAM page is already open, ~125 more when it isn't** at libDaisy's timings (RM0433 FMC chapter; `libs/libDaisy/src/dev/sdram.cpp:84-90`).
- **Measured on the module** (round 6): 10 cycles a float for one sequential SDRAM stream, 33 for 32 interleaved streams (the tank's pattern), 48 for writes, ~100 for a delay line's read-then-write; 3 for the same 32-stream pattern in AXI SRAM; `expf` 113, `sinf` 90, `powf` 209, `log10f` 158.

### 2.2 The instruction count of the tank (from the disassembly)

The `cost-tank` agent counted every instruction `Fdn::process` runs in the steady state (no SIZE crossfade), from `firmware/build/immensio_versio.elf` at `0x0800c0e8` (5,700 B, 1,645 static instructions; I re-ran the histogram myself: 251 `vldr`, 82 `vstr`, 11 `vdiv`, 23 `vmrs`, 0 `vfma`, 166 branches, 145 stack-relative accesses). Per **tank sample** (24 kHz):

| Configuration | Line loop | Output + early taps | Hadamard + writes | **Total instructions** | VDIV |
|---|---|---|---|---|---|
| MASSIVE (8 lines, 2 in-loop allpasses each, 4 taps a line, Neve) | 1,488 | 1,084 | 395 | **2,967** | 16 |
| HALL, large SIZE (no in-loop allpasses, 2 taps) | 832 | 716 | 395 | **1,943** | 16 |
| HALL, small SIZE (allpasses in, 2 taps) | 1,488 | 716 | 395 | **2,599** | 16 |
| Round 8's test tank (6 taps) | 1,424 | 1,452 | 395 | **3,271** | 16 |

What that count says about the code, as compiled:
- **Per line per sample, ~30 loads and ~12 stores are the line's own state going to memory and back** (`readNow_`, `interp_`, `absorbY_`, the allpass glide positions, the coefficients, `xfLeft_` reloaded three or four times because the compiler cannot prove the line-buffer stores don't alias it). Only ~120 of ~750 memory instructions a tank sample touch delay-line data. The 8-line loop is not unrolled, so no two lines' chains overlap.
- **The 8×8 Hadamard mix (24 butterflies) runs through the stack**: ~217 instructions a sample where the arithmetic is 24 adds.
- **Each early tap costs ~23 instructions** (two float-to-int converts, a `full()` test, index maths) for two loads and four FP ops of real work; MASSIVE's 32 taps are 740 of the 1,084 "output" instructions.
- **Two divides per line per sample:** the allpass interpolator's `eta = (1-f)/(1+f)` (this one has to move with the read) and `LoopEra`'s `/ drive`, where `drive` is exactly 1.0 in every era but the cassette.
- **~12 compare-and-branch pairs per line per sample**, 10 of them `vcmp`+`vmrs`, which is single-issue and waits for the compare.
- No `vfma` (so `-ffp-contract=off` is doing what it says), no libm call per sample, no `vsqrt` per sample.

### 2.3 Why the arithmetic costs what it does: round 8 reconciled

Round 8 measured the small test tank at **4,049 cycles a sample with its memory in AXI SRAM**. The count above gives it 3,271 instructions plus ~100 for its share of `control()`: **about 1.2 cycles per instruction**, including ~300 cycles of AXI waits. The M7 can in principle issue two instructions a cycle; this code gets one. The reasons are structural: each line is one dependent chain (read → eta → divide → allpass → allpass → loss filter → ERA → divide), the lines run one after another, and ten compare/branch pairs a line each stall the pipe. The `lit-m7` agent ran the same tank's compiled code through an instruction-level emulator with a cache model and got 3,386 dynamic instructions a sample, the same picture. Its lower bound for the same arithmetic perfectly scheduled is ~1,900 cycles; a realistic hand-tuned figure is 2,500-3,000. **So about a third of the tank's arithmetic time is schedule, not maths.**

### 2.4 The real MASSIVE tank: memory is ~60 % of its time

Round 9b measured the MASSIVE tank's loop at ~28 % and its output + early taps at ~31 % of the budget. Converting the instruction counts at 1.15 cycles each and adding the round 6 memory costs per stream (33 cycles a read, 48 a write) gives 24.5 % and 17.3 %. The loop matches within 15 %; **the output side is 1.8× the model.** Working back from the measurement, the tank's memory costs about **55-70 cycles per stream-sample in situ, twice the clean round 6 figure**. The agent's explanation, which I find convincing but which is derived, not measured: with write-back + write-allocate (round 5), every miss on a line write starts a line fill and leaves a dirty line to evict later; the 16 allpass writes at the end of each line's chain queue up exactly where the 32 early-tap reads follow; and every MASSIVE stream sits in its own SDRAM row (lines are 512 KB apart, taps at quarter points, the low tank, swell and predelay interleaved), so almost every fill is a row miss behind a dirty eviction. Round 6's 33 cycles was reads only, nothing dirty.

The `lit-m7` agent's cache + SDRAM-row model, fed the firmware's real compiled code, lands 0-25 % *below* the owner's measurements on every corner (PLATE 58-63 % vs 59-69 measured; MASSIVE 104-111 % vs 115-129; HALL 74-99 % vs 101-123). It is good for relative effects, not absolute load; I use it that way below.

**The whole picture for MASSIVE with BLOOM (115-129 % measured), per 48 kHz sample, as % of the budget:**

| Part | Share | How known |
|---|---|---|

Neither is in the profile's corner table; both are now (section 3, item F).

### 2.5 Why the arithmetic costs what it does, in the owner's words

The chip does one step at a time, in order, and a reverb line is a chain of steps where each needs the one before. Eight lines could run side by side, but the code runs them one after another, so seven lines sit idle while one waits for its divide. Then every number a line needs is fetched from memory and put back every sample, because the compiler can't tell that writing a sample into a delay buffer won't change them. And the delay buffers themselves live in the slow external memory, in a pattern that defeats the cache: about eighty places are touched every sample, each in a different "page" of the memory chip, and each page change costs a fixed wait that libDaisy has set five times longer than the chip needs.

### A. The tank line by line (merged; `core/dsp/Fdn.cpp` `runBlock`, `lineFast`, `lineSlow`)

*Plain: instead of stepping all eight delay lines forward one sample at a time, each line now runs a whole 16-sample block on its own with its numbers kept in registers; then the eight results are mixed sample by sample as before. Same sums, same order, same bits.*

- **What changed.** `Fdn::process` (5,700 B, one body) became `runBlock` (2,476 B), `lineFast` (1,504 B, -O3, the everyday path: a full or filling line whose allpasses are at their exact length all block), `lineSlow` (1,236 B, -Os and flattened: a line that is crossfading, or an allpass gliding, joining or leaving), `tapsMoving` and `tapsOld` (the early taps when their positions move or during a crossfade). The crossfade is line-major too: the rotation's per-sample gains are stepped ahead into a 32-entry array, so the old per-sample loop, `xfLines` and `xfOldTaps` are gone. The Hadamard runs on locals; still reads (the low tank: no modulation) compute their allpass coefficient once a block; still taps on a full line read two to a pass with the sample's sum in a register; `LoopEra` runs over the block and skips the divide when `drive == 1.0f`; the Midiverb box is one shared out-of-line copy (which also took 772 B out of `Plate::process`).
- **Why it is bit-identical.** A line's read at sample s uses only samples written ≥ di back, and every real line is ≥ ~250 samples long while a block is ≤ 32; the per-line chain (read, allpasses, loss, ERA, interpolator state) belongs to one line, so running it in sequence per line is the same sequence of operations; the Hadamard needs all eight outputs per sample and runs in a second pass in the same sum order; the writes happen after all reads, which is safe because no read in the block reaches a sample the block writes. `blockFits` checks exactly that for every line, tap and old crossfade position (`lo ≥ m + 4` and `hi + m + 4 ≤ mask`); if it ever fails the block runs one sample at a time, which is the old order. For a line that is still filling after a lazy clear, the taps and the read reproduce `ago()`'s silence sample by sample.
- **Evidence.** `SAME 55/55` after every commit; `SAME 55/55` again with the one-sample fallback forced on every block (`IV_FORCE_ONE`) and with the slow paths and moving taps forced for every line (`IV_FORCE_SLOW`), in the agent's scratch copy; the cost-tank six-scenario harness (a crossfade and a reset) byte-identical; my own run of the harness on the merged branch, `SAME 55/55`; ctest 17/17. M7 instructions per tank sample, steady, from the release disassembly: **MASSIVE 1,488 (was 2,967), 8 VDIV (was 16); HALL large 1,024 (was 1,943); the low tank 1,408 with 0 VDIV.** Per line-sample: 78 instructions for the line (1 VDIV, 14 loads of which 9 are stack reloads, 4 stores, 5 branches, 2 VMRS) plus 29 for ERA at the Neve (no divide); the baseline was 184 with 2 VDIV and ~10 VMRS. Per call there are ~2,750 instructions of set-up not in those totals (~2.5 % of the budget at the 16/8 and 8/4 call sizes). Desktop ns per tank sample (ratio only): MASSIVE 180.9 → 115.9, HALL 115.3 → 87.4, small HALL 161.3 → 95.8, low 196.5 → 149.9.
- **Saving.** At CPI 1.15 and the Engine's call sizes: **−10 % of the budget in MASSIVE, −6 % in HALL large** by count. Memory: each line's reads are now a sequential burst (round 6: one sequential stream costs 10 cycles a float against 33 interleaved; the swell's tap-by-tap change was the same idea), so 0 to −10 more, unverified until the module runs it.
- **Flash.** Release 112,180 → 111,940 B (−240): the Fdn rewrite +528 B, the shared box −772 B in the Plate.
- **Risks.** (1) The SIZE crossfade: the desktop says crossfade blocks are 4-18 % *slower* than before (the out-of-order core liked eight independent chains), the M7 count says ~15 % cheaper (4,900 instructions a tank sample against 5,700); **the new `SIZE .3<>.8` corner measures it; read its `max`.** (2) Two paths to keep in step (`lineFast` and `lineSlow`); the forced-path renders are the test, and any future change to the tank's per-sample maths goes into both. (3) `runBlock` uses ~4.2 KB of stack inside the audio callback; the stack is in DTCM with ~70 KB of room after the Engine moved there. (4) The profile's sections moved: the line-output sums and the governor are now in `kTankMix` (they were in `kTankOut`), and marks are per block (no more ~1 % marking cost); compare with round 9b with that in mind.
- **Not done:** unrolling each line's loop by two (GCC did not interleave the two samples; +680 B; its value depends on whether VDIV blocks the FPU, which `vdivIndep` now measures); reducing the per-call set-up.

### B. The twin's input side only while there is a twin (merged; `Engine.cpp`)

*Plain: the second reverb that plays over a frozen pad has its own input filters and swell, and they were running all the time; now they run only while that second reverb exists.*

`twinDiffuser_` (8 allpasses a sample in DTCM) and `twinSwell_.processBlock` ran every sample regardless of `twinActive_`, and after a MASSIVE freeze the twin swell's `tapMix_` stayed 1.0 (its attack is set only while `twinActive_` and `Swell::reset()` keeps it), so it read 24 taps a sample from a ring of silence until power-off, in every space. Guarded by `twinActive_`, read once a chunk. Bit-identical because without a twin its input is shut (`twinIn_` 0: only a freeze opens it, and that starts a twin), a freeze clears its diffusers and swell before it starts one (`onGesture`), and their output is read only while it runs. Evidence: `SAME 55/55` plus the agent's 24 long cases (twin stop, refreeze, flips, paints; blocks 48 and 37). Saving ~2.5-3 % always, ~7 % more after any MASSIVE freeze. +64 B.

### C. The Plate's reads and taps (merged; `Plate.cpp`, `Memory.h` ExactLine)

The 14 output taps' delays (`1 + offset·k`, with `k` per chunk) and `ap2`'s allpass read (its length is fixed within a chunk, so its fraction, coefficient and divide were recomputed 32 times) are worked out once a block with the same float operations; full-ring reads skip the fill tests behind a steady flag checked once a block; one shared `tapRead` replaces 14 out-of-line calls with push/pop. `Plate::process` 1,128 → 841 instructions a sample, 8 → 6 VDIV; 3,166 → 2,208 B (with A's shared box). About −3 % per Plate (a frozen PLATE runs two). Desktop PLATE −22 %. −160 B.

### D. Each tank's ERA sent only when it changed (merged; `Engine.cpp`)

`LoopEra::set` computes `2/2^13` with `exp2f` and a 5 Hz coefficient with `expf` for every line of every tank every chunk (16-24 pairs per chunk, ~255 cycles each); the Engine now compares the new `EraMix` with the last one sent, field by field and bitwise, and skips the call when equal; `eraMix` is computed once per `applySpace` instead of twice. −1.7 % in HALL/MASSIVE with ERA at rest (−2.5 % frozen), −0.2 % in PLATE. +184 B. A jittering ERA reading on the module would defeat it (the knob question in 5.1 again).

### E. The still-lows split on locals (merged; `Engine::processTwoTanks`)

The three biquads per channel reloaded every coefficient and state from memory every sample because the stores through `bufL_`/`wetL_` could alias the members; they now live in locals for the chunk, the same sums in the same order, the double power sum kept (changing it would change the governor's input). 261 → 126 instructions a sample, ~−1.35 %. −88 B.

### F. The BBD's and radio's per-block maths (merged; `EraStages.h`)

`BbdStage::set` returns early when `t` and the rate are unchanged (bitwise) and its six SVFs share one `sin`/`cos`; `RadioStage::set` recomputes its t-and-rate-only part only when they move (the wanders and RNG still run every chunk); the radio's per-sample `sinf` for the hum is skipped when the hum amplitude is exactly 0 (ERA ≤ 0.95: `x + 0·s == x`; the harness found no sign-of-zero case). −2.3 % at the radio corner and −1 % at the BBD with ERA at rest, −0.4-0.6 % with ERA moving. +328 B (the largest cost of the set; if flash is short this is the item to trim).

### G. The Engine object in DTCM (merged; `firmware/main.cpp`)

*Plain: the reverb's own working numbers (24 KB) sat in the same cached memory as the delay lines and kept getting pushed out of the 16 KB cache by them; now they live in the chip's zero-wait memory.*

`gEngineStorage` (24,232 B) gets `IV_DTCM`; DTCM holds 61,096 B with 69,976 B left for the stack (it grows down from the top of DTCM; `Engine::process` uses ~1.1 KB plus the ISR/HAL frames and `runBlock`'s 4.2 KB). The model counts AXI fills falling from 15.7 to 0.7 a sample and flash (rodata) fills from 4.2 to 2.5: **−9.1 points in MASSIVE, −7.3 HALL S0, −5.8 HALL S1, −1.5 PLATE, −8.8 cassette.** 0 B of flash; addresses only. Needs the module: the model's absolute numbers run low, and the cache-conflict share is simulated.

### H. The in-loop allpass lines in AXI SRAM (merged; `Fdn::prepare`, `Engine::attachMemory`)

*Plain: the 32 short delay lines of the MASSIVE / small-HALL diffusion (16 per tank) are a quarter of the tank's trips to the slow external memory; they fit the chip's own 512 KB SRAM, which was almost empty.*

`Fdn::prepare` takes a second arena for `apLine_`; `Engine::attachMemory` takes an `axi` array (`Engine::axiFloats` = 256 KB for the 24 kHz tank + 128 KB for the 12 kHz low tank + the cache-set stagger = 433,984 B; the firmware declares it in `.bss`, which libDaisy places in AXI SRAM; AXI now 452,024 of 524,288 B used). The twin's 256 KB stay in SDRAM (640 KB in all would not fit; exact-length rings, 86 KB a tank, would, but need the compare-wrap read in `Fdn::process`). The release's per-sample code is instruction-for-instruction the baseline's; only three literal-pool words differ. Saving: the model says −6.8 points alone, −5.2 on top of G; cost-tank's bracket is −6.5 % (round 8's AXI-vs-SDRAM rate) to −12.5 % (the in-situ 55-cycle rate) in MASSIVE and a small HALL, 0 in a large HALL (no allpasses), and about half that once F1 is in. **Caveat found tonight:** round 6's `axi32 = 3.0` measured nothing (its test array was never written, so GCC folded the reads away; the profile build now writes it, so round 11's `axi32` is the first real figure); the AXI estimates here rest on round 8's real AXI tank. +104 B.

### F1-F4. What only the module can answer (profile build; `firmware/main.cpp`, `firmware/README.md`)

## 4. Undoing the trade-offs

**The 24 kHz tank: keep it.** The tank (with the low tank) is ~70 % of the budget at 24 kHz; at 48 kHz its per-sample work doubles, so even the whole merged neutral set plus the SDRAM timing (−40 to −55 points, if the module confirms all of it) would not pay for it: MASSIVE would land around 150-170 %. The audible consequence of 24 kHz is a tail that stops at 11-12 kHz and 2-2.7 dB less white-noise level; the classic units the owner's references are modelled on ran at 20-32 kHz (Dattorro's design at 29.8 kHz, the Lexicon 224 at 20 kHz, the EMT 250 at 32 kHz; Dattorro Part 1 §1.1 footnotes 5-6), and Valhalla's Dark Room mode downsamples the whole reverb on purpose (Costello, "Algorithmic reverbs, distortion and noise"). If the owner ever misses the top octave, the cheaper question is a brighter *dry/early* path, not a faster tank. The Plate stays at 48 kHz; the opposite move (the Plate at 24 kHz, −8 to −12 % per Plate, both Plates then fit AXI SRAM) is an option the owner has not been asked about and PLATE already fits the budget.

**The 12-point swell: the 24 points are affordable, by a different route.** With today's block reads, 24 points cost ~10 points more (desktop `Swell::processBlock` 1.77-1.91× at 24; the M7 tap loop is 18 instructions a tap-sample and the count doesn't change it; +360 B of flash if adopted) — not affordable. But the swell runs at 48 kHz in front of a tank that discards everything above ~12 kHz (K above): inside the 24 kHz path it costs half, so **24 points at 24 kHz cost about what 12 points cost today**, and with whole-sample taps its spectrum is within ±0.2 dB of the 48 kHz swell's (measured on white noise at attack times 0.5-2 s, smear on and off; the 48 kHz swell's own linear interpolation droops 1.4 dB at 11 kHz, so whole-sample taps at 24 kHz would be a touch brighter at the very top). The restructure moves the swell after the halfband `down()` (linear, so the order with the swell doesn't matter for what the tank hears) and keeps `kDirectBelowSeconds`, the smear lengths and the twin's S-curve, all in seconds. `IV_SWELL_TAPS=24` on the branch renders the exact pre-v1.0.35 swell for comparison. Whether the owner wants the 24 points back is a separate question (they picked 12 on `swell_points` and are listening to seeds); the cost is no longer the reason to refuse.

**The early reflections (6 → HALL 2 / MASSIVE 4): six are nearly affordable again, and three warped taps do the job of four.** After the tank rewrite a still tap costs ~12 instructions a tap-sample (two to a pass; was 23-30): MASSIVE's 32 taps are 384 of its 1,488 instructions a tank sample, and six taps a line would be 576, **about +1.5-2 % of the budget over four.** The other finding is that the taps' layout matters more than their count: on the owner's own dip metric (`tools/render_review_pages.sh:544`, reproduced to within 0.3 dB), positions warped toward the line end (`u^0.75`) give **three taps the score of today's four** (mean dip 2.22 vs 2.17 dB; worst 3.3 vs 4.4) and six warped taps 1.54 against today's 1.78; velvet-style jitter inside each slot did not help. Either way it is a sound change (positions move), so a page if the owner wants it. Keeping HALL at two is fine: HALL's early taps are at a lower level and its dip was never the complaint.

## 5. Architecture and implementation

**Verdict.** The Core is in better shape than most embedded audio code at this stage: the Core/Host split is clean (grep: `core/` includes only its own headers and the standard library; no `getenv`, no I/O, no virtual functions, no RTTI, no allocation in `process()`), the test suite is strong on sound properties, and all 14 suites pass under AddressSanitizer and UBSan (float-cast-overflow included; the `arch` agent built and ran it). The weak points are at three edges: where the Core meets the outside world (hosts, knobs), where the desktop meets the module (arithmetic, block structure), and where one block meets the next.

### 5.1 Bugs found (none of them in the profile's corners)

1. **On the module, SIZE may never take effect** (`core/dsp/Fdn.cpp:353-360, 370`; `core/dsp/Engine.cpp:607`). SIZE is marked `Slewed` in the ParamSpec, which the Engine implements as *no smoothing* (the FDN does the moving). `Fdn::control` resets the crossfade's rest timer whenever any line's target moves by more than half a sample in a block, and the crossfade only starts after 50 ms of rest. MASSIVE's lines are ~24,000-67,000 samples long and their length is exponential in SIZE, so a knob wobble of ±2·10⁻⁵ (about 1.3 LSB of a 16-bit reading) moves a line by a sample or more, crosses a prime boundary, and resets the timer. The `arch` agent simulated it: with ±2·10⁻⁵ of noise added per block, as `AudioCallback` feeds the pot, MASSIVE's SIZE 0.62 → 0.30 **never took effect in 9 s**; HALL fails from ±2·10⁻⁴. The firmware feeds `hw.GetKnobValue()` straight through (`firmware/main.cpp:1106`, libDaisy's 2 ms one-pole) with no deadband, and the release build has never been played with knobs since v1.0.34 (the owner played the plugin; the profile build reads no knobs). While a move is pending, the in-loop diffusion amount and the SIZE/DECAY trims wait too. Also by design, a slow LFO into SIZE's CV holds the tank still until the CV rests: worth an explicit decision. A knock-on: every memo (`AbsorbMemo`, `Drift`, `Memo1`, `TapeOut::set`) keys on exact float equality, so a jittering knob defeats them (1-11 % slower on the desktop with ±2·10⁻⁴ on every knob). **Fix:** a relative hysteresis on the mean length in `applySpace` (0.1 % of the mean, under 2 cents; built tonight behind `IV_SIZE_HYST`, section 3) and/or a Schmitt-style hold on each pot reading in the firmware. The owner should confirm the real knob noise: a per-knob standard deviation readout in m0test would settle it.
2. **The half-rate stage inserts one zero sample the first time a host sends an odd block mid-stream, and the wet is one sample late from then on** (`core/dsp/HalfRate.h:19, 47-56`). Measured by the `arch` agent: an identity tank fed DC at block 32 then 17/31-sample blocks outputs exactly 0 at the switch; through the Engine, HALL's output then matches the block-48 render only when delayed one sample (−27 dB vs −3 dB undelayed). The module always sends 32 + 16 (both even), so it never hits this; the Plugin does whenever a host splits a block (offline bounce remainders, automation points), and so does the Renderer's last partial block. **Fix:** start the stage primed with one queued zero (a constant 21 µs of extra wet latency; it changes every golden's bits, not its sound). Built tonight behind `IV_HALFRATE_PRIME`.
3. **Plugin only: a mono input track gives the right output the left output as its dry** (`plugin/PluginProcessor.cpp:93, 99`; `Engine.cpp:902-903`). With `inR = inL` pointing at channel 0, the Engine writes `outL` into channel 0 and then reads it as `inR`. Measured: at MIX noon the right channel's error is −7 to −8 dB re the right output. **Fix:** copy channel 0 to channel 1 first; document in `Engine.h` that `out` may alias only the same channel's `in`.
4. **One NaN, Inf or 1e30 input sample poisons the tanks until `reset()`** (no input guard in `Engine::process`; `softClip` turns ±Inf into NaN; the limiter passes NaN). Plugin and Renderer only (the ADC can't produce them). **Fix:** once per chunk, `if (!(level == level)) reset();` on the governors' power, which goes NaN within one chunk.
5. **The prime sieve is unsynchronised global state** (`Fdn.cpp:35-53`): ThreadSanitizer reports a data race when two Engines prepare on two threads (a host opening two plugin instances). On Apple silicon an instance can see `gSieved` before the table's stores and get composite "primes". Fine on the module (one Engine, sieved in `main`). **Fix:** a namespace-scope static initialiser.
6. **The twin outlives its sound by ~25 s** (`Engine.cpp:844`): it switches off when its governor level, a 1.5 s power smoother, falls under −100 dB; that smoother falls at 2.9 dB/s whatever the tail does, so after every unfreeze the second tank runs **26-30 s** in every space while its audio is gone in 2-8 s. **Fix:** judge on the fast (50 ms) level, or stop at a level where the twin is below the output's noise (not bit-identical: an output below −100 dB stops being added).
7. **The twin's input side runs when there is no twin, and after the first MASSIVE freeze its swell reads 24 taps a sample until power-off** (`Engine.cpp:798-799, 810`; `applySpace` sets the twin swell's attack only while `twinActive_`, and `Swell::reset()` keeps the attack, so `tapMix_` stays 1.0; measured on the desktop with a debug accessor, still 1.0 after a flip to PLATE). Costs ~2 % always and ~7 % after any MASSIVE freeze, for nothing audible. Fixed bit-identically tonight (section 3).

### 5.2 Structure

- **The Engine is three components and a policy object in one class**: `Engine.cpp` is 961 lines; `process()` 171, `controlTick` 170, `applySpace` 224. `applySpace` computes and pushes the voicing for three tanks plus the twin, ERA's loop and wet stages, the diffusers, the swell, the shimmer, the predelay and the hiss. `controlTick` is ducking, diffuser motion, parameter smoothing, freeze glides, pad and tail capture, paint, the SPACE flip state machine and the predelay crossfade. The same "reset the twin" block appears three times (`Engine.cpp:158-162, 267-271, 693-700`). Six public test hooks and two `#ifndef IV_FIXED_VOICINGS` prototypes live in the product class; one of them costs the product path (`decayMakeup_`'s `powf(x, 1)` every chunk). The `arch` notes sketch a behaviour-preserving decomposition (an `InputStage`, `SpaceTank`, `FreezeController` + `TwinVoice`, `SpaceFlip`, `WetStage`, a pure `Voicing` function from smoothed params to targets, and one `EngineDebug` struct for every hook, recorded in the sidecar), proved step by step with the bit-identity harness. The pure `Voicing` is the main gain: today the only way to test a mapping decision is to render audio.
- **The control path runs twice per firmware block** (`Engine.h:135`: `kChunk = Fdn::kControlBlock = 32`; a 48-sample block becomes 32 + 16). Since v1.0.35 the FDN runs at 24 kHz and gets 16 + 8 samples a chunk, so its 32-sample control block never fills and the coupling has lost its reason. Consequences: every per-chunk task runs twice a millisecond; every memo keyed on the chunk length (`Memo1`, the governor's `dt_`, `Drift`'s `wcArg_`) misses every chunk because `dt` alternates (measured: HALL at block 48 calls `expf` 130 times a block, at block 32/64/96 only 37-111, i.e. 2.7 vs 1.16 per sample); and **the Plugin at any DAW buffer that isn't 48 produces different samples from the module** (measured: blocks 32, 64 and 96 give identical output to each other; block 48 differs from them by −22 to −31 dB), which breaks SPEC §2.3 rule 6 across block patterns. Fixes: a firmware block of 64 or 96 (0 B of flash, +0.33 or +1 ms latency, the module then chunks like the desktop), or an absolute control grid (`clock_ % kChunk == 0`), or `kChunk = 48`. None is bit-identical to today; all are inaudible in kind (a control rate of 1 kHz instead of an irregular 1.5 kHz).
- **ParamSpec and Mappings are not quite the single source of truth**: `smoothingMs` is unused for SIZE (the `Slewed` tier is not implemented), SPACE and ATTACK; `Engine::kLimitThreshold` duplicates `voicing::kLimitCeiling` and is unused; a dozen time constants are literals in `dsp/` (`Engine.cpp:324, 476, 592, 582, 751`; `Plate.cpp:161, 185`; `Era.h:84`). Dead code: `Filters.h`, `Select.h`, `Seed.h` are included nowhere; `IV_NO_UNSWITCH` and `IV_INLINE` unused; `Swell::process` (the per-sample reference) unused and untested against `processBlock` as its comment promises; `Oversampler`'s `kFactor == 4` branch, `latencySamples`, `groupDelay` unused. Stale Resilio comments in `Oversampler.h:24-25`, `Seed.h:2`, `SizeOpt.h:13-26`. SPEC §5.2 still puts the Plate in AXI SRAM and the filter states in DTCM; the code takes both from the SDRAM arena and the Engine object. SPEC §6.2 lists files that don't exist.

### 5.3 Idiom for the M7

- **Per-sample divides**: 18.6 per output sample at the Neve (8 allpass `eta`, 8 `LoopEra /d`, plus the Plate's or the still-lows'), **45 in the cassette** (the tape's 13 per channel per call), 26 in the radio (`arch` F11 lists every site). Most divide by per-block constants. `x / 1.0f` is exact, so the `/d` goes for free in every era but the cassette; the rest become reciprocals only at the cost of last-bit changes.
- **Per-sample `std::` maths**: one real call, the radio's `sinf` for the hum, which runs even when the hum amplitude is 0 (ERA ≤ 0.95). `std::sqrt` compiles to `vsqrt` plus an errno-path `bl sqrtf` stub because `-fmath-errno` is on; `-fno-math-errno` is bit-exact and removes the stub.
- **Double precision** is used once per sample in `processTwoTanks` (the low tank's power sum, a `vmla.f64` chain): the H750's FPU is FPv5-D16, so it's hardware, ~0.2 %, but unnecessary over 32 samples (a float sum would change the governor's input in the last bits).
- **Branches in hot loops** are mostly loop-invariant per chunk and well predicted; the per-read `full()` test and `ExactLine::at`'s three compares per read (28 of them a sample in the Plate's taps) are the exceptions.
- **Aliasing**: no `__restrict` anywhere, so `this->` fields and the output pointers are reloaded every sample. Local copies fix it without a contract change; `__restrict` must wait until bug 3's aliasing contract is written down.
- **Data layout**: `Fdn` is struct-of-arrays (`float[8]` per field, one cache line each), fine as long as the lines stay resident; but the hot per-sample state of the whole Engine (24-25 KB, in AXI SRAM, cached) competes with the SDRAM line traffic for the 16 KB data cache. DTCM has ~90 KB free (model: −9 points in MASSIVE from moving the Engine object there; section 3).
- **`IV_SIZE_OPT` is GCC's `optimize` attribute**, which GCC's manual says is for debugging only; it works here and the bytes are measured, but treat each use as something to re-measure after a toolchain change.
- **Sample-rate-dependent per-sample constants** (`Engine.cpp:766, 835, 862, 821`; `Output.h:43`; `Fdn.cpp:263` `kA`, which now runs at the 24 kHz tank rate so its "~5 ms" is 10 ms on the module): they make the Plugin at 44.1 or 96 kHz differ from the module. Derive each from a time constant in `prepare()`.

### 5.4 Numerical robustness and real-time safety

- **Denormals**: nothing sets `FPSCR.FZ` or `FPDSCR.FZ` (no `vmsr` in the release disassembly; libDaisy leaves them at reset = 0), so the callback runs IEEE-compliant subnormals. The Plugin flushes them (`juce::ScopedNoDenormals`). Arm says the M7 FPU handles subnormals "in hardware, no support code" (TRM §1.2.4, §8.2.2); whether that costs cycles is **undocumented and unmeasured**, and the profile's signal (a click plus −66 dBFS noise) can never show it. The interrupt context takes its FPSCR from FPDSCR, so a fix must set both. Built into the profile build tonight with a MICRO test that times a one-pole decaying through the subnormal range (section 3).
- **Stability**: `readAllpass` keeps the fraction in [0.5, 1.5), so `eta` ∈ (−0.2, 0.33] and the interpolator's pole stays well inside the unit circle; the SIZE crossfade's gain `xfK_` is capped at 1.42 for at most 0.3 s (the one place loop gain > 1 is allowed by design: SPEC §2.3 rule 2 should say so); the governor's makeup is bounded by `kMakeupMaxRate`.
- **Counters and buffers**: `clock_` is 64-bit; `pos` is masked; `fill` saturates; `ago()` and `ExactLine::at` are correct across wraps; the HalfRate queue is safe for any n ≤ 32 (`queued_ ≤ 1`); `Arena::take`'s skew uses at most 127 × 8 floats per slice, 108 slices against 256; `primeAtOrAbove` terminates (the sieve covers a 96 kHz host's longest line; beyond it, trial division). `kMaxEdges` = 16 drops the 17th edge in a block but self-heals at the next (levels are set, not toggled).
- **Real-time safety**: no allocation, locks, exceptions or unbounded loops in `process()`. The one-shot sieve runs in `main()` before `StartAudio` (~2 ms). The crossfade's per-sample helpers (`xfLines`, `xfMix`, `xfAllpass`, `xfOldTaps`) are `IV_SIZE_OPT` (-Os) and `IV_NOINLINE`, called per line per sample for 0.3 s at a time: that breaks `SizeOpt.h`'s rule ("never per sample") exactly when the load peaks.
- **The firmware never checks `engine.ready()`**: a failed arena allocation would ship as a silent passthrough with normal LEDs. A boot LED pattern would show it.

### 5.5 Test strategy

What the 14 suites cover is strong on sound properties (T60s, holds, paints, loudness, clicks, goldens). What they lacked, with what was done tonight:
- **A committed bit-identity harness**: `tools/same_render.py` (55 renders; this review's gate). The 66-render scripts that proved v1.0.35-36 lived in a scratchpad and were lost.
- **Host-contract tests**: nothing covered odd block sizes through the half-rate stage, mono aliasing, non-finite input, 17+ edges. Two are now tests on the branch (SIZE under knob noise; the half-rate hole); mono aliasing and NaN recovery are described above with their fixes.
- **The desktop's arithmetic isn't the firmware's**: `libiv_core.a` has 828 fused multiply-adds (Apple clang's default `-ffp-contract=on`; `CMakeLists.txt` sets no FP flags) where the firmware has none; the desktop uses Apple's libm, the firmware newlib's. In gain-1 loops (frozen pads, infinite tails) last-bit differences grow over minutes, so hold behaviour measured on the desktop is a close cousin of the module's, not the same run. One line fixes the contraction (`-ffp-contract=off` on `iv_core`; goldens then need a no-sound-change update).
- **The tests depend on uncommitted stimulus**: a fresh worktree fails `test_era` and `test_metrics` until `tools/make_stimulus.py` has run (I hit it tonight). A CTest fixture would generate them.
- **The profile corners hold every setting still**, so they miss the SIZE crossfade, the frozen twin, SHIMMER, knob noise and memo misses, and they include the hook overhead (~10-14 marks a sample, ~1.5-3.5 % of the budget, estimated). Corners for the first three are on the branch now.
- Also worth doing: a counting build (`IV_COUNT_OPS`: SDRAM reads, libm calls, divides per section, as a desktop regression gate), a per-symbol flash gate (`nm -S` diffed against the last commit; with 460 B left the total gate catches problems too late), `ctest -j8` (the suites are parallel-safe under ASan; serial Release takes 221 s), and QEMU's `mps2-an500` (a Cortex-M7) for firmware-identical bits on the desktop (feasibility unverified).

### 5.6 Flash: where ~3-4 KB could come from

From `nm -S` of the release ELF: `Engine::queueEdge` is **604 B** at -O3 for a 4-line insertion sort that runs once per edge (mark it `IV_SIZE_OPT`: ~450 B); the implicit constructors `Engine::Engine()` 1,628 B + `Fdn::Fdn()` 984 B at -O3 (67 `memset` calls over `.bss` that is already zero; explicit `IV_SIZE_OPT` constructors: 0.5-1.5 KB, needs a build to confirm); newlib's `sinf`/`cosf` with their soft-double range reduction ~2.2 KB (a polynomial sine for the control-rate LFOs is not bit-identical, ~1e-6 error). `gOddComposite` is 8.9 KB of AXI SRAM sized for a 96 kHz host (RAM, not flash). Measured tonight: the 2× tape frees 808 B, the Plate's full-ring fast paths 708 B, the FWHT on locals 164 B, dropping libDaisy's `-fno-move-loop-invariants` for the DSP objects 70-88 B in `Fdn.o`, `processTwoTanks` on locals 72 B.

## 6. Technique against the literature

The DSP audit of 22 Oct (`docs/research/dsp-audit.md`) already compared each engine with Dattorro, Jot, Smith, Schlecht and Costello and was not redone. Three agents read the sources again tonight with a different question: not "is it built from the research" but "what do the sources say about doing the same for less, and where is ours weaker". Every source below was fetched (Appendix A); anything the agents could not fetch is marked.

### 6.1 The FDN (HALL, MASSIVE)

- **Structure.** An 8-line FDN with a unitary (Hadamard) feedback matrix and in-loop allpasses is the structure the literature recommends for a hall (Jot 1997 §2; Smith PASP "FDN Reverberation", "Zita-Rev1"; Schlecht's thesis ch. 2; Costello's "Getting started, part 2" names Stautner & Puckette and Jot as the foundations). Jot's loss rule (loss ∝ each line's own length) is met exactly at DC and Nyquist by our per-line shelf; the residual is the in-loop allpasses' frequency-dependent group delay, which the loss filter doesn't see: a 3-8 % T60 spread per line (derived from the allpass coefficients). Low priority; Jot's remedy is a tonal-correction filter on the wet (~10 ops a sample), which changes the balance at every setting and would need the owner.
- **Density.** Exact path counting over our prime lengths (Schlecht ch. 5's echo lattice) says HALL at 100 ms of mean line reaches 2,000 echoes/s at ~300 ms and Abel's η = 0.9 at ~0.9-1.1 s; MASSIVE at 2 s takes ~10 s to 2,000 echoes/s and >25 s to η = 0.9, which is why MASSIVE needs its in-loop allpasses and early taps. The 24 kHz rate changes none of these (the lattice is in seconds). Where the structure is sparsest: a small HALL's bass (the 12 kHz low tank with 35 ms lines), and the first second of a big HALL, which the input diffusers hide; no metric in the repo would see a repeating smeared burst there (an autocorrelation of the tail's energy envelope would).
- **Cheaper structures.** Schlecht & Habets 2020 ("Scattering in FDNs", arXiv 1912.08888) show that a *filter feedback matrix* (each matrix entry a short FIR of delays, e.g. "velvet" scattering) lets a small FDN reach the echo density of a big one. The `lit-fdn` agent's stand-alone simulation (its own code, not the paper's) found **4 lines with a 3-stage velvet feedback matrix reach 8 plain lines' mixing time at the same total delay** (η 0.9 at 235/940/2,310 ms vs 265/835/2,425 for 35/100/260 ms means); plain 4 lines are 6-7× slower. The paper's Table I puts the matrix at 24 adds, 4 multiplies and 32 delay accesses a sample; the per-line work (reads, loss, ERA, taps, drift) halves. Estimated 25-35 % of MASSIVE's budget, 15-25 % of HALL's, but **it changes the voice of both spaces** (the owner's early-tap, in-loop-diffusion and still-lows picks were all made on 8 lines; the stereo field has 4 rows to draw from; the paper reports ~20 % modal-decay error at K = 3 with a lumped loss filter against a 5 % JND). A desktop prototype behind a hook, listened to, is the only way to know; it is the last item in section 8. Householder instead of Hadamard, velvet-noise FIR tails and feed-forward diffusers were all judged not worth it here (the FWHT already costs 24 adds; the others cost more reads than they save).
- **Modulation.** Ours (±1-2 cents at ~0.3 Hz per line, HALL's floor 3× deeper, DRIFT's Wander up to ±20 cents at 1-2.25 Hz with rates fanned ±50 %) sits inside what Dattorro (Table 1: excursion 16 samples at 29.8 kHz; footnote 14), Costello ("Modulation in reverbs", 2009; "Stability through time variation", 2010: Ursa Major's rate-spread random delays) and Schlecht (time-varying matrices spread a tone into narrow noise with no pitch glide, smooth to ~4 Hz) describe. Modulating only 4 of 8 lines is an established economy (Dattorro modulates two of his plate's reads) but saves under 0.5 % here; the allpass interpolator is the right choice for a loop (magnitude 1: a cubic shaves highs every pass), with Dattorro Part 2's known small transient each time the read crosses a whole sample.
- **Still lows.** The two-tank idea is only half supported by the sources: Keith Barr's dual-band reverb and Eventide's H90 Hall split the band, but the published reason is tone, not modulation; nothing found states "don't modulate the lows" as a rule. It was heard and approved (ADR 0012 amendment), which is the evidence that counts here.
- **Changing length without pitch bend.** The SIZE crossfade (ADR 0025) is exactly PASP's "Large Delay Changes" recipe (crossfade between two reads rather than glide); no cheaper established way exists. What the sources don't cover is its cost inside a loop: every line read twice and the old taps re-read for 0.3 s, plus a per-tap `exp` per block for the level correction (up to 40 `std::exp` a chunk for ~3 s after a move: ~1.4 % of the budget). Cheaper mitigations (stagger the lines' fades, ramp the old taps down fast instead of reading them for 0.3 s, drop the per-tap exp) change the sound slightly and need the owner.
- **Delay-length choice.** 16 % of HALL SIZE positions and 7 % of MASSIVE's give two lines an exact order-2 dependency (one length twice another, or a sum); Schlecht's spread σ for MASSIVE at low SIZE (1.11) is below his recommended range, which is the owner's "echoes to wash" character, not a fault. A dependency-aware prime picker at control rate costs nothing.

### 6.2 The Plate, the diffusers, the swell, the shimmer, the twin

- **Plate vs Dattorro (1997).** Topology, lengths, coefficients and taps match the paper (re-checked). What the audit did not say: ours runs the paper's 29.8 kHz design at 48 kHz (1.6× the samples); Dattorro modulates **two** reads where we make **eight** allpass-interpolated reads a sample, each with a divide; the 14 output taps are 14 calls to an out-of-line `lerpRead` with a fill test and up to three wrap compares, recomputing `1 + offset·k` every sample although `k` only changes per chunk; `ap2`'s interpolator is static within a chunk yet recomputes its divide every sample; both Plates (270 KB each, power-of-two-free but sized for SIZE 1.59 so the write pointer sweeps all of it) sit in SDRAM although SPEC §5.2 planned the Plate for AXI SRAM. Count: ~900 instructions and ~46 memory operations a sample against Dattorro's ~85 flops and ~38 memory operations, and MI Rings' ~60 flops in 16-bit (MIT). Half the Plate's cost is memory. Two bit-identical fixes measured tonight (full-ring fast paths, −708 B of flash, PLATE −16 % on the desktop; tap positions per chunk) and one placement question (the Plate fits AXI SRAM only at 24 kHz or with SIZE capped near 1.3; both Plates fit at 24 kHz).
- **Blooms.** No published structure gives an exact, controllable slow bloom for fewer memory streams than our 12 taps + 3 smear allpasses: the established blooms (Barr's Midiverb II "Bloom" and Costello's Shimmer and Supermassive) are recirculating allpass networks where the attack comes from feedback and diffusion inside the loop, which trades away the exact attack time the owner chose (the audit's S2). Velvet noise (Välimäki 2017) at its 40-100 pulses/s would need 80-200 taps a side. What the sources do say: smoothness comes from what follows the taps, not from the taps (Välimäki §3.2's four Schroeder allpasses "fill the gaps"); and Barr puts the most audible flutter at 4-8 Hz, which for our 12 taps is an attack time of 1.2-2.4 s (a hypothesis for where the audit's pulsing peaks; untested). The real economies are rate and placement: **the swell runs at 48 kHz in front of a tank that discards everything above ~12 kHz**; at 24 kHz it costs half (desktop: 0.94 → 0.52 ms per second of audio) and with whole-sample taps its spectrum is within ±0.2 dB of today's (linear interpolation at 24 kHz would lose 1-3 dB above 4 kHz in the swelled part). That is also how to afford the 24-point version the owner heard (section 4).
- **Early reflections.** Dattorro's plate has none apart from its 14 taps; Barr's are a tapped delay with *decaying* weights; MI has none. Our taps rise with position and sit on a perfectly regular grid (`(k + (i+0.5)/8) / n`), which combs; velvet-style jitter inside each slot did not improve the owner's dip metric, but positions warped toward the line end (`u^0.75`) did: **3 warped taps match today's 4 on that metric** (mean dip 2.22 dB vs 2.17; worst 3.3 vs 4.4). Ears decide; the metric is noisy.
- **Shimmer.** The cheap shifters in the sources (Clouds' and DaisySP's two-head linear crossfade, Barr's single-sideband frequency shifter) are what the owner rejected over four rounds. Ours (8 sin² heads a side with random onsets behind an 8th-order 6 kHz filter) costs ~850 instructions, 16 divides and 32 float reads a sample: **10-19 % of the budget when on**, against ADR 0024's "~300 cycles (estimate)". It also records every sample in every ATTACK mode (the 8 biquads and two SDRAM writes: ~2 % always). Economies that keep the sound: record at 24 kHz (an octave up then reads exactly one stored sample per output sample: no interpolation, whole-sample offsets; the 6 kHz filter already makes decimation safe), a divide-free window (a smoothstep of a triangle, within 0.01 of sin², eight heads summing to exactly 4), and recording only while SHIMMER is selected (the first ~0.8 s after switching lacks the octave of what was just played).
- **The twin.** No source has a second tank for playing over a frozen pad (Elements freezes with time 1 and input 0; Clouds raises the reverb amount; Supermassive's infinite mode lets the input accumulate, which is our paint). The twin is our own, like the swell. Economies: a smaller twin (12 kHz, no early taps, fewer lines: 10-35 % of the budget while frozen), or a fixed small plate twin in every space (~8-10 % against 25-60 %); all audible changes to playing over a pad.

### 6.3 The ERA stages

- **Tape at 2× instead of 4×.** Oversampling is the standard first remedy in all four papers read (Parker/Zavalishin/Le Bivic DAFx-16; Bilbao et al. 2017; Holters DAFx-19; Dattorro). Measured tonight on the tape alone (power not at harmonics, five tones averaged as `test_era` does): at normal levels 2× is as clean as 4× below ~7 kHz; it aliases only for strong content near and above ~10 kHz (0.9 amplitude at 11 kHz: −19 dB at 2×, −39 at 4×). In the Engine, `test_era`'s alias figure moves from −32.9 to −32.4 dB (limit −32; the 4× figure is itself only 0.9 dB under it), third-octave bands of real renders differ by ≤ 0.2 dB. **Antiderivative antialiasing is not an option here**: the play-operator hysteresis is not a function of its input (Holters' stateful extension needs a scalar-input nonlinearity), its antiderivative needs a `log` per high-rate sample, and ADAA does nothing where the alias actually comes from at low level (the operator's corners).
- **The BBD** already is Raffel & Smith's minimal chain (DAFx-10: anti-alias filter, the clock's sample-and-hold, the NE570 compander, reconstruction filter); Holters & Parker 2018 is heavier, not lighter. The savings are in how it computes (shared `sin`/`cos` for the six SVFs, `set()` only on change, reciprocals).
- **The AM radio** already does its fading at control rate with per-sample glides, as the Watterson / ITU-R F.1487 models do. What costs is a `sinf` every sample for a hum that is 0 until ERA 0.95, five divides and a square root a sample, and a `set()` that recomputes 8 `powf`, 11 `expf`, 3 `sqrtf` and 16 trig calls every chunk whether or not the knob moved. Smith's recurrence oscillators (PASP "Digital Sinusoid Generators") replace the `sinf` when the hum is on.
- **LoopEra in the tank** divides by `drive` every line every tank sample, and `drive` is exactly 1.0 in every era but the cassette; `x / 1.0f == x` in IEEE for every x. Its `set()` recomputes two constants (`2/2^13` and a 5 Hz coefficient) with `exp2f` and `expf` for every line of every tank every chunk: 1.7-2.6 % of the budget for nothing.

### 6.4 The platform (ST, Arm, CMSIS, DaisySP, MI)

- **SDRAM timing.** libDaisy programs `RPDelay = 16` and `RCDDelay = 10` SDRAM clocks (`libs/libDaisy/src/dev/sdram.cpp:84-90`, with the comment "started at 2"); the AS4C16M32MSA-6 datasheet (AC table p. 17) needs tRP = tRCD = 18 ns, which at the 100 MHz SDRAM clock is 2 clocks (3 with margin). libDaisy issue #408 records 16 as a placeholder that nobody retuned ("up to 5 % going from 16 to 1" in ReverbSC; one user hit faults at 1). Every page change in the tank's pattern pays the extra 20 clocks (~96 CPU cycles), and the model counts ~17 page changes per output sample in MASSIVE. This is the largest single sound-neutral lever found tonight and the one that most needs the module: the profile build now reprograms the timing, re-runs the round 6 micro-tests at both settings, and checks 8 MB of SDRAM for errors (section 3). libDaisy also refreshes the SDRAM every 20.5 µs where the datasheet asks 7.8 µs (reliability at temperature, not speed).
- **Memory placement.** AN4891 (§2.3.2, Table 8): DTCM is zero-wait, uncached, with two 32-bit ports the M7 can use in parallel; AXI SRAM is cached and ~11 cycles a line; flash with the I-cache is within 6 % of ITCM on ST's FFT benchmark (Table 9), but that benchmark fits the I-cache and ours doesn't (the Engine's hot code is ~21-30 KB against a 16 KB 2-way I-cache: the model counts ~1,000 I-cache line refills per 48-sample block, 3-6 % of the budget). The release firmware uses 42 KB of AXI SRAM (so ~470 KB is free, not the ~200 KB the brief assumed), 36 KB of DTCM (~90 KB free) and none of the 64 KB ITCM. MI's `fx_engine.h` (MIT) and DaisySP keep hot state on chip and long lines in SDRAM as 16-bit; DaisySP's `ReverbSc` is a plain 8-line FDN with jittered delays, written for readability rather than the M7.
- **Compiler.** `-ffp-contract=off` is right (quinapalus and the Arm thread: VFMA blocks dual-issue with loads and chains at 3-5 cycles; Resilio's bench found ~9). Of the other flags tried on the firmware's own compiled code, only two are bit-exact and help: dropping libDaisy's `-fno-move-loop-invariants` for the DSP objects (−1 % instructions, −88 B in `Fdn::process`) and `-fno-math-errno`; `-O2` is a flash lever (−2.7 KB on `Fdn::process`) at +17 % instructions; `-fno-trapping-math` makes it *worse* (speculated divides). CMSIS-DSP's float kernels on a non-SIMD M7 are scalar loops with an unroll by 4 and one accumulator: nothing there a per-sample reverb needs.
- **Denormals**: see 5.4. **PLD** does preload a cache line on the M7 (PM0253 §3.4.7) but only two fills can be in flight and the FMC serves one request at a time; round 7's whole-block prefetch stalled for that reason. A rolling one-line-ahead PLD per stream is a different experiment (a MICRO test on the branch).

## 7. Sound and musicality

Separate from cost. Each item names its source and what it would cost; none is built.

- **HALL's long tail resonances and MASSIVE's highs** are already in `docs/research/valhalla-comparison.md` (HALL's floor was tripled for it, v1.0.25; MASSIVE's highs ring as long as its body since v1.0.31). The remaining item there, Supermassive's larger pitch movement at long settings (29-35 cents on the vibes against our 6.6), is a DRIFT comparison for the owner.
- **Early reflections warped toward the line end** (`u^0.75`): three taps matched today's four on the dip metric; six warped taps scored 1.54 against 1.78. If MASSIVE's early energy is revisited, warped positions are the cheaper and (by the metric) smoother layout. Ears decide.
- **The swell's pulsing**: Barr's 4-8 Hz flutter band predicts the audit's pulsing peaks at attack times of 1.2-2.4 s. More tap jitter there would be free. A different jitter seed per hit (the `swell_seed` machinery exists) would stop repeated hits blooming identically.
- **A symmetric bloom** (Costello on Sagittarius: "slow to get going, slow to go away"): below ~70 % feedback his tail fades in and out over similar times; ours decays by DECAY after the slab. A mapping where low DECAY tracks the attack would give MASSIVE that family's symmetry for 0 CPU. **Pointillistic echoes** (Supermassive's DENSITY): the BLOOM smear gain (0 to 0.5) is exactly that axis and already exists as a constant.
- **Plate**: Dattorro warns that slight modulation reads as vibrato on piano; worth a held-piano check of the plate's wander. A ping-pong WIDTH (swap the output taps' sides) is free. Costello ships "smooth" and "dirty" plates as modes; ERA already is the dirt.
- **Shimmer**: an octave-plus-fifth layer (ratio 3) costs one more head set; a small feedback (0.2-0.3) into the pre-tank path becomes viable once the shimmer records at 24 kHz with whole-sample reads (no interpolation loss to pile up; ADR 0024 set feedback aside for the splices piling up); reversed heads give the "bloom shimmer" ValhallaShimmer users name.
- **Small HALL's bass** is the sparsest part of the design (the 12 kHz low tank at 35 ms of mean line): a longer mean for the low tank in small rooms, or a sub-cent wander in it, both change the bass character and need listening.
- **A dependency-aware prime picker** (section 6.1) removes the exact order-2 length coincidences at 16 % of HALL's SIZE positions for 0 cycles.
- **SIZE under CV**: by ADR 0025's rest rule a slow LFO into SIZE holds the tank still until the CV rests. For a modular user that is a behaviour to decide on, not a bug.
